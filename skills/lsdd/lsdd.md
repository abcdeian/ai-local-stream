# LSDD — Layered Spec-Driven Development（分层规格驱动开发）

> **核心理念：不直接改代码，通过维护分层 Spec（规格文档）来控制整个软件代码的生成。**

LSDD 是 SDD（Spec-Driven Development，规格驱动开发）的分层演进版本，是一种面向 AI 代码生成的方法论。它将软件的需求、架构、领域设计逐层 Spec 化，形成一套**自上而下、可追溯、可增量更新**的多层规格文档体系。每一层 Spec 既是上层的展开，也是下层生成的输入。当最底层 Spec 就绪后，AI 可直接从 Spec 生成工程代码；当业务变动时，只需修改对应层级的 Spec，再由系统自上而下级联刷新，最终重新生成代码。

### 与传统 SDD 的区别

| | 传统 SDD | LSDD                           |
|---|---------|--------------------------------|
| Spec 结构 | 单层或扁平的规格文档 | 四层分级 Spec，逐层细化                 |
| 生成方式 | Spec → Code（一步到位） | L1 → L2 → L3 → L4 → Code（逐层展开） |
| 变更传导 | 改 Spec 后全量重新生成 | 级联更新，仅影响相关链路                   |
| 领域建模 | 可选 | 内置 DDD 领域划分，Spec 天然按领域组织       |
| 适用规模 | 中小型项目 | 中大型项目，领域复杂度高的系统                |

## 一、整体分层架构

```
┌─────────────────────────────────────────────────┐
│  L1  用例场景层  (Use-Case Layer)                │  ← 人工维护
├─────────────────────────────────────────────────┤
│  L2  架构设计层  (Architecture Layer)            │  ← 基于 L1 生成 + 人工约束
├─────────────────────────────────────────────────┤
│  L3  领域层      (Domain Layer)                  │  ← 基于 L2 逐领域展开
├─────────────────────────────────────────────────┤
│  L4  组件层      (Component Layer)               │  ← 基于 L3 逐组件展开
├─────────────────────────────────────────────────┤
│  CODE  工程代码  (Generated Code)                │  ← 由 L4 直接生成
└─────────────────────────────────────────────────┘
```

**信息流方向：L1 → L2 → L3 → L4 → Code**

每一层只依赖其上层的输出，下层不反向影响上层定义。

## 二、各层详细说明

### L1 — 用例场景层 (Use-Case Layer)

| 项目 | 说明 |
|------|------|
| **维护方式** | 人工编写与维护 |
| **存放目录** | `docs/use-cases/` |
| **核心目的** | 描述软件的使用场景和使用用例，作为 DDD 领域划分的源头输入 |

#### 包含内容

1. **业务场景描述**：系统面向的用户角色、核心业务目标、关键业务流程的自然语言描述。
2. **用例清单**：每个用例包含——
    - 用例编号与名称
    - 参与角色 (Actor)
    - 前置条件 / 后置条件
    - 主流程 (Main Flow)
    - 异常流程 (Exception Flow)
    - 输入 / 输出数据概要
3. **用例间关系**：include、extend、泛化等关系的说明或图示。
4. **验收标准 (Acceptance Criteria)**：
    - 每个用例必须附带可验证的验收条件（Given-When-Then 或检查清单形式）
    - 关键业务规则的明确断言（边界值、状态转换、权限约束等）
    - 作为后续代码生成后自动化测试的依据

#### 作用

- 是整个 LSDD 文档体系的**唯一需求入口**。
- 后续所有层级的生成均以此为根基。
- 采用 DDD 模式，通过用例聚类来识别限界上下文 (Bounded Context) 和业务领域 (Domain)。

#### 特别说明

> **L1 用例层只描述业务场景，不包含技术定义。**
>
> - **禁止出现**：API 接口定义、方法签名、对象/参数结构、枚举定义、类型映射等技术细节
> - **应该出现**：业务角色做什么、流程步骤是什么、异常时怎么处理、验收标准是什么
> - **尽量避免**技术参数（如具体端口号、线程数、缓冲区大小等），除非该用例本身就是一个技术对接场景（如插件配置规格说明）
> - 所有技术定义（接口契约、数据结构、枚举、异常体系等）**统一下沉到 L2 架构设计层**

---

### L2 — 架构设计层 (Architecture Layer)

| 项目 | 说明 |
|------|------|
| **维护方式** | 基于 L1 自动/半自动生成 + 人工审定与约束补充 |
| **存放目录** | `docs/structure-design/` |
| **核心目的** | 将用例场景转化为领域架构，划分领域，定义全局约束 |

> **L2 是所有技术定义的唯一归属层。** 所有接口定义、外部常量、枚举、配置规范、数据结构、类型映射、异常体系等技术细节，**必须且仅在 L2 中定义**。L1 不包含任何技术定义，L3/L4 只引用 L2 已定义的内容，不得自创。

#### 包含内容

1. **统一语言 (Ubiquitous Language)**：
    - **术语表 (Glossary)**：对项目中所有关键业务术语进行明确定义，消除二义性。每个术语包含：
        - 中文名 / 英文名
        - 定义与语义说明
        - 所属领域
        - 示例 / 反例（可选）
    - **命名映射**：术语到代码命名的映射规则（类名、方法名、变量名等），确保代码与业务语义一致
    - **约束**：所有下层 Spec（L3、L4）和生成代码必须严格使用统一语言中定义的术语，禁止自造同义词或缩写

2. **领域架构图**：
    - 核心域 (Core Domain) 划分
    - 通用域 (Generic Domain) 划分
    - 支撑域 (Supporting Domain) 划分
    - 领域间依赖与协作关系

3. **核心逻辑描述**：
    - 关键业务流程的语义描述（流程图 / 时序图 / 文字）
    - **只描述子域之间的调用与数据流转关系**，不展开子域内部的实现细节
    - 子域内部的流程、结构、状态机等属于 L3（领域层）的内容
    - 聚合根 (Aggregate Root) 与核心实体的初步识别
    - 领域事件 (Domain Event) 的初步定义

4. **全局约束与规范**：
    - **代码规范**：命名约定、包结构规则、分层原则
    - **配置规范**：配置文件格式、环境变量管理方式
    - **技术规范**：技术选型、框架版本、依赖管理策略
    - **通用定义**：全局枚举 (Enum)、常量 (Constants)、工具类 (Utils) 的定义与职责边界

5. **接口契约 (Interface Contract)**：
    - **仅定义子域之间的接口**，子域内部接口属于 L3
    - 领域间的服务接口定义（RPC / REST / 事件）：方法签名、语义、调用方向
    - 请求 / 响应数据结构（DTO）定义：字段、类型、必填 / 可选、约束
    - 错误码与异常处理约定（统一错误码体系、重试策略）
    - 版本策略与兼容性规则

6. **状态与生命周期模型**：
    - 核心实体的状态定义与合法状态转换图
    - 生命周期阶段划分（创建 → 活跃 → 归档 / 销毁等）
    - 跨领域的状态同步规则与一致性约束

7. **质量约束**：
    - 性能要求、可用性要求
    - 安全约束、数据一致性要求

#### 与 L1 的关系

- L2 与 L1 **等价映射**：每个用例场景都能追溯到 L2 中的某个领域或业务流程。
- L1 是"做什么"，L2 是"怎么组织"。

---

### L3 — 领域层 (Domain Layer)

| 项目 | 说明 |
|------|------|
| **维护方式** | 基于 L2 逐领域自动/半自动生成 |
| **存放目录** | `docs/structure-design/<domain>/domain-<domain>.md` (每个领域一个目录，目录下 domain-<domain>.md 为领域文档) |
| **核心目的** | 对 L2 中某一个领域做深度分解，明确其内部结构和对外依赖 |

#### 包含内容（每个领域一份文档）

1. **领域概述**：
    - 所属限界上下文
    - 核心职责与能力描述
    - 对外暴露的接口 / 服务契约

2. **外部依赖声明**：
    - 依赖的其他领域及其接口
    - 依赖的通用域（如通用工具、公共枚举）
    - 依赖方式（同步调用 / 事件驱动 / 共享内核）

3. **内部结构图**：
    - 内部功能模块的划分
    - 模块间的调用关系与数据流

4. **核心流程**：
    - 领域内关键业务流程的详细描述
    - 状态机 / 流程图（如适用）

5. **状态与生命周期模型**：
    - 领域内核心实体的状态机定义（状态、事件、转换条件）
    - 非法状态转换的拒绝策略
    - 状态变更触发的领域事件

6. **功能聚类**：
    - 将内部功能进一步划分为若干**组件 (Component)**
    - 每个组件的职责边界说明

#### 作用

- 是 L2 到 L4 的桥梁。
- 确保每个领域的边界清晰、职责单一。

---

### L4 — 组件层 (Component Layer)

| 项目 | 说明 |
|------|------|
| **维护方式** | 基于 L3 逐组件自动/半自动生成 |
| **存放目录** | `docs/structure-design/<domain>/CP-XXX-<component>.md` (与所属领域的 domain-<domain>.md 同目录) |
| **核心目的** | 领域内某个组件的完整技术设计，可直接生成代码 |

#### 包含内容（每个组件一份文档）

1. **组件概述**：
    - 所属领域
    - 组件职责与边界

2. **内部结构图**：
    - 类 / 接口的组织结构
    - 核心类之间的关系（继承、组合、依赖）

3. **核心流程**：
    - 模块内关键流程的详细描述（伪代码级别）
    - 方法调用链路

4. **技术细节与要求**：
    - 数据结构定义（字段、类型、约束）
    - 算法说明（如适用）
    - 线程安全要求
    - 异常处理策略
    - 性能约束

5. **功能小块 (Functional Block)**：
    - 按抽象层次拆分为若干功能小块
    - 每个功能小块通常**直接对应一个类或接口**
    - 每个功能小块包含：
        - 类名 / 接口名
        - 职责说明
        - 公共方法签名与语义
        - 关键私有方法说明
        - 依赖注入点

6. **依赖约束（关键原则）**：
   > **组件是内聚的。** 组件不依赖外部其他组件，仅依赖：
   > - 所属领域层 (L3) 定义的公共接口
   > - 架构层 (L2) 定义的通用定义（Utils 类、枚举、常量等）

#### 代码生成

- L4 文档就绪后，AI 可**直接从 L4 生成工程代码**。
- 生成的代码包括：类文件、接口文件、单元测试骨架、配置片段等。

## 三、生成流程

```
人工编写 L1 (用例场景)
       │
       ▼
  系统生成 L2 (架构设计)  ←── 人工审定 + 补充约束
       │
       ▼
  系统生成 L3 (领域层)    ←── 按领域逐个展开
       │
       ▼
  系统生成 L4 (组件层)    ←── 按组件逐个展开
       │
       ▼
  系统生成 Code (工程代码) ←── 直接从 L4 生成
```

### 生成规则

1. **逐层生成**：必须上层完成后，才能生成下层。
2. **可审可改**：每层生成后，人工可审阅、修改、补充约束，再进入下一层。
3. **可追溯**：每一层的每个元素都能追溯到上层的来源。
4. **幂等性**：相同的输入文档，应生成一致的输出。

## 四、变更管理

### 场景一：用例更新

当业务发生变化，新增或修改了用例场景时：

```
修改 L1 (用例)
   │
   ▼
级联更新 L2 (架构)  → 识别受影响的领域
   │
   ▼
级联更新 L3 (领域)  → 更新受影响领域的文档
   │
   ▼
级联更新 L4 (组件)  → 更新受影响组件的文档
   │
   ▼
重新生成 Code        → 仅重新生成受影响的代码
```

**原则：自上而下级联更新，变更范围最小化。**

### 场景二：约束增加 / 修改

可以在**任意层级**增加人工约束，例如：

| 层级 | 约束示例 |
|------|----------|
| L2 架构层 | 新增全局代码规范、更换技术框架、新增通用枚举定义 |
| L3 领域层 | 调整领域间的依赖方式、新增领域事件 |
| L4 组件层 | 增加线程安全要求、修改数据结构、调整算法实现 |

约束增加后的更新流程：

```
在目标层级增加约束
       │
       ▼
  级联更新该层级以下的所有文档
       │
       ▼
  重新生成受影响的代码
```

**约束不向上传播**：在 L4 增加的约束不会影响 L3/L2/L1。

## 五、目录结构与文件对应

```
docs/
├── lsdd.md                          # 本文件 — 方法论说明
├── use-cases/                       # L1 用例场景层
│   ├── overview.md                  #   用例总览
│   └── UC-XXX-<name>.md             #   单个用例文档
└── structure-design/                # L2 架构设计层 + L3 领域层 + L4 组件层
    ├── architecture.md              #   L2 — 领域架构图与子域划分
    ├── constraints.md               #   L2 — 全局约束（代码/配置/技术规范）
    ├── common-definitions.md        #   L2 — 通用定义（枚举/常量/工具类）
    └── <domain>/                    #   每个领域一个目录（L3 + L4 共存）
        ├── domain-<domain>.md       #     L3 — 领域文档（领域概述、内部结构、核心流程）
        └── CP-XXX-<component>.md    #     L4 — 该领域下的组件文档（每个组件一份）
```

## 六、核心优势

1. **文档即代码源**：代码完全由文档驱动生成，文档是唯一的真实来源 (Single Source of Truth)。
2. **变更可控**：任何变更都通过文档层级传导，变更影响范围清晰可见。
3. **AI 友好**：分层结构化的文本天然适合 AI 理解和生成。
4. **人机协作**：人工负责需求和关键决策（L1 + 各层约束），AI 负责展开和代码生成。
5. **领域驱动**：以 DDD 为理论基础，确保架构合理、边界清晰。
6. **增量更新**：变更时仅更新受影响的链路，避免全量重建。
