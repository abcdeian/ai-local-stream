# LSDD — 分层规格驱动开发执行技能

## 概述

本技能将项目 `docs/lsdd.md` 中定义的 LSDD 方法论落地为可执行流程。用户提供一段需求描述，本技能负责：

1. 理解需求内容，定位其在 LSDD 四层体系中的影响范围
2. 自上而下逐层修改对应的 Spec 文档
3. 最终基于最底层（L4）文档生成或修改工程代码

## 前置准备

每次执行前，必须完成以下准备：

1. **读取方法论文档**：读取 `${lsdd-skill-install-dir}/lsdd.md`，理解四层 Spec 体系的定义和规则
2. **读取现有文档结构**：扫描 `docs/` 目录，掌握当前所有层级文档的分布
3. **理解用户需求**：分析用户输入，确定需求类型和影响层级

## 核心执行流程

### 第一步：需求分析与影响定位

分析用户输入的需求描述，判断：

- **需求类型**：新增用例 / 修改用例 / 新增约束 / 修改约束 / 新增领域 / 修改组件 等
- **起始影响层级**：需求从哪一层开始变更（L1？L2？L3？L4？）
- **影响范围**：哪些领域、哪些组件会被波及

输出一个变更计划，列出需要修改的文档清单和修改顺序，等待用户确认后再执行。

### 第二步：逐层修改文档（自上而下级联）

严格按照 **L1 → L2 → L3 → L4** 的顺序，从起始影响层级开始，逐层修改：

#### L1 — 用例场景层 (`docs/use-cases/`)

- 文件：`overview.md` 或 `UC-XXX-<name>.md`
- **规则**：
    - 只描述业务场景，禁止出现技术定义（API、方法签名、枚举、类型映射等）
    - 包含：业务角色、操作动作、流程步骤、异常处理、验收标准（Given-When-Then）
    - 技术定义统一下沉到 L2

#### L2 — 架构设计层 (`docs/structure-design/`)

- 文件：`architecture.md`、`constraints.md`、`common-definitions.md`
- **规则**：
    - L2 是所有技术定义的唯一归属层
    - 接口定义、枚举、常量、配置规范、异常体系等必须且仅在 L2 定义
    - 只描述子域之间的调用与数据流转，不展开子域内部实现

#### L3 — 领域层 (`docs/structure-design/<domain>/domain.md`)

- 每个领域一份 `domain.md`
- **规则**：
    - 描述领域内部结构、核心流程、功能聚类
    - 引用 L2 已定义的接口和通用定义，不得自创
    - 将功能划分为组件，明确每个组件的职责边界

#### L4 — 组件层 (`docs/structure-design/<domain>/CP-XXX-<component>.md`)

- 每个组件一份文档，与所属领域的 `domain.md` 同目录
- **规则**：
    - 包含完整技术设计：类/接口结构、核心流程（伪代码级）、数据结构、方法签名
    - 功能小块直接对应一个类或接口
    - 组件不依赖外部其他组件，仅依赖所属 L3 公共接口和 L2 通用定义

### 第三步：基于 L4 文档生成/修改代码

L4 文档修改完成后，根据 L4 中的功能小块定义：

1. 定位对应的源代码文件
2. 按 L4 描述的类结构、方法签名、流程逻辑修改代码
3. 确保代码与 L4 文档严格一致
4. 如有新文件需要创建，按项目现有包结构和命名规范放置

## 关键原则

### 信息流单向性
- 信息流方向：L1 → L2 → L3 → L4 → Code
- 每层只依赖其上层输出，下层不反向影响上层
- 约束不向上传播：在 L4 增加的约束不影响 L3/L2/L1

### 逐层执行，不跳层
- 必须上层完成后才能修改下层
- 每层修改后，向用户展示变更内容摘要，再进入下一层
- 禁止跳过中间层直接修改底层

### 变更范围最小化
- 识别受影响的领域和组件，仅更新相关链路
- 未受影响的文档和代码保持不变

### 可追溯性
- 每层的每个元素都能追溯到上层来源
- 修改时在变更摘要中说明追溯关系
